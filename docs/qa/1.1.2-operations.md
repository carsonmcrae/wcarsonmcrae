## Scheduled cleanup evidence

The configured `17 * * * *` trigger belongs to the correct production service, whose deployed
artifact exposes both `fetch` and `scheduled`. At 18:58 UTC, the dashboard and scheduled-only
GraphQL history still returned no events, including a lifetime query without a cron filter and
an ownership check without a script filter. No trigger, logging or retention setting was changed.

All 43 expected hourly `:17` D1 metric buckets from November 5, 00:17 UTC through November 6,
18:17 UTC contained activity. Quiet buckets consistently contained two read-classified queries;
an empty delete can report no rows written. Those aggregate counts corroborate execution but
cannot establish either statement's success or an individual scheduled invocation's outcome.

The async handler itself is valid: Cloudflare's public runtime registers its returned promise
with `waitUntil` and waits for the result. Adding an explicit wrapper is not a supported fix for
the missing history. Cloudflare documents [Cron Events](https://developers.cloudflare.com/workers/configuration/cron-triggers/#view-past-events)
separately from optional request logs. Existing D1
[query analytics](https://developers.cloudflare.com/d1/observability/find-expensive-queries/)
can provide a narrower verification: filter the two exact parameterized cleanup statements on
the server, restrict the database/time range, and return only aggregate success counts/timestamps.
Never retrieve visitor parameters or broad query history to diagnose this gap. The follow-up
pull-request receipt records the actual outcome of that read-only boundary check.

That exact-statement SQL Analytics check found successful samples for both cleanup statements at
November 6, 18:17:56 UTC, using existing credentials and no settings change. Sampling-weighted
counts estimated 43 rate-limit and 37 retention executions; these are not exact invocation totals.
The timestamp is the latest retained sample, not a complete latest-ever history. This directly
verifies execution of both cleanup statements while leaving formal cron-invocation outcomes
unavailable. No trigger re-registration or handler change was needed.

## Recovery boundary

Read-only production metadata identified database creation at November 4, 23:27 UTC. Current and
November 4, 23:30 UTC Time Travel bookmark queries succeeded. The database was less than two days
old, so it could not demonstrate seven days of actual history. Cloudflare's
[documented Free allowance](https://developers.cloudflare.com/d1/reference/time-travel/) is seven
days; generic errors for pre-creation and older probes did not establish a more precise cutoff.
Bookmarks remain private. No production export or restore was used to test that boundary.

An isolated remote D1 rehearsal used one newly created temporary database and the exact reviewed
0001–0003 migration SQL. Inventory and shared UTC-day row/storage quotas were checked first;
mutation guards excluded the production database and required the newly returned test identity.
All fixtures were synthetic, with no Worker binding or account-plan change.

The baseline had permanent total three and two retained reaction rows after an erasure. Deliberate
damage changed only that temporary database's rows, total, index and trigger. Time Travel restored
the exact baseline, including schema objects and the independently retained total. The returned
undo bookmark restored the exact damaged state; a third restore recovered the baseline again.
A subsequent vote, duplicate and erasure verified the restored increment trigger, uniqueness and
permanent total four. The rehearsal read 186 and wrote 40 SQL rows. The temporary database was then
deleted, and inventory verification confirmed that only the original production database remained.

This proves a real provider restore/undo path with synthetic data, alongside the existing local
SQLite recovery regression. It does not prove recovery of every historical production point or
authorize overwriting production. Production restoration still needs an exact approved checkpoint,
maintenance/write coordination and reconciliation of newer totals and erased identifiers, as
described in the [operations guide](../../workers/reactions/OPERATIONS.md).
