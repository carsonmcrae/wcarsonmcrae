## Windows WebKit cold-module investigation

Fixed three-sample fresh-context runs used the same baseline bytes on Astro HTTP/2 and a separate
HTTP/1.1 TLS fixture. Chromium photo click-to-open was 71–88 ms; WebKit was 3.65–4.64 seconds on
Astro and 1.99–4.66 seconds on the fixture. Fixture module handlers took 0.9–3.25 ms; Astro viewer
transfers took 21–23 ms after delayed request starts. One fixture browser resource interval was
3.59 seconds despite roughly 2 ms of server handling. Server handling and browser delivery/scheduling
are different measurements; this evidence does not identify an upstream root cause.

A second controlled experiment alternated three paired samples per engine using identical baseline
HTTP/1.1 bytes, except replacing the three JavaScript preload-dependency-map calls with empty arrays
in memory. Four preload links became zero. Chromium original/no-preload ranges were 64–87/65–68 ms.
WebKit originals were 3.48/3.49/4.52 seconds; no-preload samples were 3.97/0.984/5.034 seconds.
Removing those maps does not reliably eliminate the Windows delay. Favorable later assembled-app
samples (WebKit 230–473 ms) have other confounding changes and do not prove a fix. Workstation load
was shared; these are fixed diagnostic samples, not an exclusive-idle benchmark or production SLA.
No retry, timeout increase or weaker assertion was used to turn this timing observation green.

The final image failure on `6fe161c` selected the 320-pixel candidate, but its request had no
recorded response/completion before the unchanged readiness predicate expired. A later fixed
four-sample interleaved control kept those application bytes and Astro HTTPS unchanged. Default
Playwright routing disables WebKit resource caching globally, including assets outside the route's
URL matcher. Repeated external SVG fetches delayed native image dispatch: request-to-server-arrival
was 3,030–3,769 ms with routing versus 58–64 ms without it. Server handling was 1.55–1.94 ms in both
conditions; response delivery followed server completion by 7–15 ms. Both selected the correct
320-pixel image for a 213-pixel slot. This identifies the fixture-induced image delay, not a general
WebKit, production-network or HTTP/2 defect. A diagnostic fetch shim was not retained.

The replacement `reaction-proxy.ts` fixture uses real HTTPS/CORS through an ephemeral loopback
CONNECT proxy for the reserved reaction host. Assets bypass it and keep native caching. Native
mutations/unknown service paths still fail the per-test guard; intentional `page.route` fixtures
still override reads and writes. Four fixed native WebKit samples passed all eight original image
selections in 2.09–2.38 seconds. Real TLS tests enforce boundaries, failure cleanup and 100% coverage
of this helper. Assertions, five-second readiness deadlines and zero retries are unchanged.

The proxy's unit client now trusts only the ephemeral fixture certificate, whose SAN covers the
reserved host. Twenty real TCP/TLS cases include rejection of an untrusted authority and a trusted
certificate used with the wrong hostname. Certificate verification stays enabled; no scanner
finding is dismissed or suppressed. The final PR receipt checks CodeQL's separate result and alerts.

The first integrated run passed all 57 test bodies but failed 19 desktop teardown guards because
full Chromium also attempted browser-process CONNECTs to its own background service. An isolated
capture confirmed five denied `www.google.com:443` tunnels and two successful reserved-host tunnels.
All non-reserved tunnels remain denied with 403 and no upstream connection. A separate coarse
blocked-tunnel counter prevents attributing browser-process traffic to application reaction writes;
the strict service request guard and rejection tests remain intact. The original image case then
passed once in each of desktop Chromium and Windows WebKit. Final integrated receipts are in the PR.
