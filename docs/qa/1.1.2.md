## Responsive images and scrolling

At 1440 CSS pixels, 236-pixel Timeline covers previously selected 800-pixel images at both DPRs.
At DPR 1, three representative screenshot covers fall from 25,946/20,628/14,648 bytes to
6,982/4,674/4,296; at DPR 2 they select 19,432/15,014/11,006-byte candidates. The wedding cover
falls from 28,900 to 8,796 bytes in WebKit at DPR 1, while Chromium retains the larger cached or
prefetched resource in that sequence. Not every cover/browser transfer becomes smaller.
Posts selects larger existing candidates when its slots need them; maximum resolution is unchanged.
Mobile and desktop candidate assertions cover both views, DPR 1/2 and the additional first-PC and
Recalen images. No photograph, alt text, accessible name, caption or native original destination
was removed to obtain these results.

The navigator regression sends 200 scroll notifications and observes one scheduled geometry scan
and no current-attribute writes for unchanged selection. Mobile and Posts presentations skip that
desktop work. This establishes reduced operations, not a measured frame-rate or latency guarantee.

A separate Chromium 153.0.8010.12 diagnostic alternated two fresh samples per variant at
1440×900, DPR 1, reduced motion, with loopback uncompressed HTTPS/no-store responses and isolated
read-only reactions. Each sample ran three cycles of native scrolling, date jumps, category and
view changes, post Back/Forward navigation, then three album open/next/previous/close cycles:
60 measured operations altogether. No command was retried. No page error, console warning or
reaction write occurred; module GETs were unique within each document. Element and document/window
listener counts stayed constant across the three cycles of each phase, and filmstrip buttons
remained eight. Finite samples and diagnostic post-GC heaps around 2.5–2.7 MB do not prove no leaks.

Full-document navigation made 78 module requests per baseline sample versus 157/156 for reviewed
samples: more smaller modules are a real tradeoff under this deliberately uncached fixture.
Timing ranges overlapped under shared workstation load. Renderer counters reset across document
loads, so only same-document CDP operation deltas are meaningful; this profile does not prove
BFCache behavior. Resource Timing separates handler, header/transfer, browser scheduling and
driver-command time. No general interaction-speed or request-count improvement is claimed.

## Windows WebKit cold-module investigation

Fixed three-sample fresh-context runs used the same baseline bytes on Astro HTTP/2 and a separate
HTTP/1.1 TLS fixture. Chromium photo click-to-open was 71–88 ms; WebKit was 3.65–4.64 seconds on
Astro and 1.99–4.66 seconds on the fixture. Fixture module handlers took 0.9–3.25 ms; Astro viewer
transfers took 21–23 ms after delayed request starts. One fixture browser resource interval was
3.59 seconds despite roughly 2 ms of server handling. Server handling and browser delivery/scheduling
are different measurements; this evidence does not identify an upstream root cause.

A second controlled experiment alternated three paired samples per engine using identical baseline
HTTP/1.1 bytes, except replacing the three JavaScript preload-dependency-map calls with empty arrays
in memory. Four preload links became zero. Chromium original/no-preload ranges were 64–87/65–68 ms.
WebKit originals were 3.48/3.49/4.52 seconds; no-preload samples were 3.97/0.984/5.034 seconds.
Removing those maps does not reliably eliminate the Windows delay. Favorable later assembled-app
samples (WebKit 230–473 ms) have other confounding changes and do not prove a fix. Workstation load
was shared; these are fixed diagnostic samples, not an exclusive-idle benchmark or production SLA.
No retry, timeout increase or weaker assertion was used to turn this timing observation green.

## Manual presentation and keyboard review

Reviewed paired baseline/assembled screenshots of Timeline and Posts at 320, 768 and 1440 CSS
pixels in both themes: 24 screenshots, six paired contact sheets. Profile, heading, pinned moments,
dock and first-card geometry match in all twelve pairs. No clipping, overlap or horizontal overflow
was observed in these captures. Differences are responsive image rasterization and three dark
mobile rail-edge pixels. This is a top-of-page presentation comparison, not every possible state.

A Windows in-app browser keyboard spot check at 1280×720 exercised Tab/Enter through the main
landmark and portrait, native photo-dialog opening, Escape closing and focus return, plus both
themes. It exposed the covered Skip to content link; the stacking correction is protected by
real-keyboard, hit-test visibility assertions in both themes. Browser regressions cover additional
menus, dialogs, no-JavaScript reading, history and responsive geometry. No screen-reader or native
Safari manual pass was performed; automated axe and geometry checks are not conformance proof.

## Required checks and limits

Focused regressions cover failed optional chunks, mount/cleanup isolation, denied/corrupt storage,
stalled request headers/body, explicit retries, retired image identities, schema health, concurrent
POST/DELETE, retention and synthetic recovery. Full coverage/built/browser/security results and
any platform-specific failures are recorded during closeout, without counting focused totals twice.

No production settings, deployment, database contents, provider retention, scheduled execution or
remote backup/restore was tested. No originals or committed image bytes changed. Automated axe,
keyboard and browser tests do not certify accessibility conformance. NVDA/VoiceOver and native
Safari manual checks have not been performed in this audit; no conformance claim is made.
