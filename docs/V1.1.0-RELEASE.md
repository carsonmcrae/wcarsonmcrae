## Architecture, security and privacy

The [overview](architecture/overview.md) describes `photo-viewer.ts` lifecycle/composition,
`photo-filmstrip.ts` navigation, `photo-reaction-controls.ts` presentation and the shared
`reaction-controller.ts` operations. The [maintenance record](architecture/maintenance.md) and
[review](architecture/review.md) identify the additive two-deployment contract.

The Worker receives keys from `reaction-targets.ts`, derived from approved content rather than an
asset-directory glob. Existing moment IDs, aliases and heart/suffix keys are preserved. Image IDs
must remain supported if their presentation is retired; never repurpose an existing identity for
a different picture. The current registry contains all current UI image sources; future additions
must keep that property.

The service implementation, SQL migrations, bindings, secret salt, logging setting and database
remain unchanged. Parameterized SQL, strict origin/JSON/UUID/body validation, SQL uniqueness,
permanent totals, 90-day identifier cleanup and separate erasure quota apply equally to image keys.
All targets share the existing allowance of 20 new reactions per network/hour. No account, upload,
analytics, remote embed or new external provider is introduced.

The client uses DOM text/property APIs for approved caption, alternative and image URL data;
the new viewer modules do not inject HTML. Optional choices use existing consent-gated namespaces.
A confirmed vote whose choice flag cannot be persisted remains selected for that visitor identity
in-session; forgetting invalidates the fallback. A late response does not recreate cleared
preferences. This is a lightweight reaction system, not identity proof or fraud-resistant voting.
The [privacy notice](../src/data/privacy.ts) now explicitly covers moment and photo keys.

- The subsequent Copy/paths/controller scope passed 57 tests, with all three measured modules at

- Real migrated SQLite tests preserve seeded preexisting moment/alias totals while independently
  adding all four image kinds. They cover duplicate submissions, the shared quota, origin rejection,
  identity erasure and retention without decrementing totals. These are isolated test databases;
  no production vote was cast by this review.
- Focused lint and formatting passed for the support/Copy files. A focused duplicate scan of the
  initial support extraction found no clones. These do not substitute for whole-tree gates after
  the remaining UI changes.

Vitest 5 can reuse a stale transformed `import.meta.glob` inventory after new image files arrive.
An initial profile-image membership failure disappeared with a fresh external cache; the JPEGs
and production asset names were correct. Clear the cache before final coverage rather than
weakening image assertions or changing application source to invalidate a cache.

The coordinating manual review used the in-app Chromium browser at 1280 pixels and 390 × 844 CSS
pixels. It confirmed the fixed outer viewer, native thumbnail controls, Next changing the photo
and caption, and the related link disappearing without changing the outer dimensions. The mobile
reaction controls used two columns. Keyboard closing restored the album trigger. Mobile PageDown
revealed the small arrows below the dock/near the bottom, while neither appeared above the profile.
This is a reported preview/keyboard check, not a native-device or assistive-technology evaluation.

The final local command sequence is below; it has not been run by this documentation review.
The candidate tag variable validates identity without creating a tag. Run serially so the root and
project-path builds do not overwrite one another.

```powershell
$env:RELEASE_BASE_SHA = git merge-base HEAD origin/main
$releaseVersion = (Get-Content package.json -Raw | ConvertFrom-Json).version
$env:RELEASE_TAG = "v$releaseVersion"
$env:PUBLIC_REACTIONS_URL = 'https://reactions.daysforth.test'
$env:PW_WEBKIT = '1'
npx vitest --clearCache
npm run validate:full
npm audit --include=dev --audit-level=high
npm audit signatures
npx --yes @sonar/scan@5.0.2 "-Dsonar.projectVersion=$releaseVersion"
```

Use the exact checked-in Gitleaks, Semgrep and Trivy invocations from
[CI](../.github/workflows/ci.yml), preserving engine/checksum pins, full development-dependency
scope and failing exit codes. Review Sonar's completed analysis and hotspots with genuine new LCOV;
scanner upload alone is not a passing quality gate. CodeQL and dependency review run separately in
the required PR workflows. `validate:full` does not include these additional scanners or manual QA.
The reserved reactions origin above is an intercepted browser-test fixture. Before publication,
rebuild the final site with the official Worker origin, and verify no fixture origin is shipped.

## Compatibility and publication order

1. Complete final gates and review the exact source/tree. Take a private, read-only snapshot of
   existing reaction totals before changing the Worker.
2. Deploy the additive Worker allowlist to the existing configured service/profile. No migration,
   database recreation, secret rotation, quota reset or blanket cleanup belongs in this release.
3. Verify the API returns valid numeric counts for the new approved image keys, while every old
   baseline key remains present with a nondecreasing count. Compare the old keys as a subset:
   exact equality of old/new key sets would incorrectly reject this intended additive release.
4. Publish the validated site through the owner-controlled PR/Pages flow. Recheck canonical and
   project-path behavior, all sitemap routes, imported JS chunks/CSS/fonts, local images and
   reaction reads. The old 1.0.1 acceptance script needs its version/page/key expectations updated.
5. Verify the plain canonical homepage carries 1.1.0 and the new controls, then record authorized
   `v1.1.0` tag/release identity and permanent visitor notes. Preserve all historical tags/dates.

Live verification should not add test votes. Existing visitors may legitimately increase totals,
so nondecrease is the compatibility invariant. Any deliberate mutation canary needs its own exact
identity/key tracking and guarded cleanup; broad deletion or subtraction is never acceptable.
